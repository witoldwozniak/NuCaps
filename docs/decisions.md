# Decisions

This document records the decisions that shape this repository, each with its reason, and the open questions that will become decisions later. It exists so that a settled question is not argued again from memory, and so that a reader can see why the project looks the way it does. Add an entry when a decision is made. Do not delete entries. If a decision is reversed, add a new one that says so and why. When an open question is settled, move it up into the sections above.

## Analysis

- **Target `net10.0` only. netstandard2.0 is deferred.** `System.Reflection.Metadata` ships inside the .NET 10 shared framework, so reading metadata needs no package reference. On netstandard2.0 the same code needs three packages and a hand-written `IsExternalInit` type before `record` and `init` compile. Revisit this if there is a concrete reason to embed `NuCaps.Core` in a Roslyn analyzer or an MSBuild task, because both of those still run on .NET Framework inside Visual Studio.
- **Read metadata with `System.Reflection.Metadata`, not Mono.Cecil.** Read-only scanning at corpus scale is what `System.Reflection.Metadata` is designed for, and it needs no package reference. Mono.Cecil is stronger at rewriting IL, which this project never does.
- **Analysis is static. NuCaps never loads or executes an assembly it inspects.** This is what makes it safe to analyze a package nobody trusts, and it is why any target framework can be read regardless of what NuCaps itself runs on.
- **Package fetching lives in `NuCaps.Cli`, never in `NuCaps.Core`.** `NuCaps.Core` accepts a package that already exists on disk, by file path or by seekable stream, and opens no network connection. A `.nupkg` file is a zip archive and needs random access, so a forward-only stream is not enough. The command line tool owns `NuGet.Protocol` and everything about resolution, package sources, credentials, caching and retries. There are three reasons. `NuGet.Protocol` pulls in nine packages, including `Newtonsoft.Json`, and every project embedding `NuCaps.Core` would inherit all of them. Untrusted packages have to be parsed in an isolated process, because the metadata reader is not hardened against malformed input, and that process should hold no credentials and open no connections. `NuCaps.Core` is also meant to be embeddable in a Roslyn analyzer or an MSBuild task, and neither of those may reach the network. Adding fetching to `NuCaps.Core` later is possible, while removing it from a published library is a breaking change, so this is the direction that stays reversible.
- **Capability profiles are per target framework, plus a computed union.** A single package ships one assembly per target framework and their capabilities genuinely differ. Reporting one arbitrary framework produces wrong answers: some assemblies bind native code through `GetProcAddress` and `dlsym` instead of P/Invoke declarations, so a profile taken from the wrong framework can report no native dependency where there are hundreds.
- **A capability claim is about a method. The package-level answer is a roll-up of those claims.** Every method in the package is checked. A package-level flag on its own cannot say which part of the package is responsible, and a reader cannot expand a flag back into detail, while detail collapses into a summary at any time. The finer form is therefore the one to compute and store. Storing it is affordable because most methods produce no record: measured on 2026-08-14, only 2.9 percent of the methods in `AWSSDK.S3` and 11.7 percent of the methods in `Azure.Storage.Blobs` reference a privileged API directly.
- **A capability claim is composed across the declared dependency closure. It is not scoped to one package.** `Azure.Storage.Blobs` performs no network operation at all. All twenty of its references into `System.Net` are header and content types, and the calls to `HttpClient.Send` and `HttpClient.SendAsync` live in `Azure.Core`. `Azure.Identity` has the same shape. A claim scoped to a single package therefore reports the wrong answer for the packages whose whole purpose is network access, and no improvement to the analysis inside one package fixes it. Composition is affordable because closures are small: on net10.0, measured closures ran from zero packages for Serilog to twenty-three for `Azure.Identity`.
- **Cache analysis results per package version, keyed by the package's content hash together with the analyzer version and the sink list version.** A published package version is immutable, so its analysis is a pure function of its bytes and can be reused forever. Key on the content hash rather than on the identifier, because a private feed or a mirror can serve different bytes under the same name, and the name is the part an attacker controls. Cache the per-package result and compute the closure view on demand, because a dependency declares a version range rather than an exact version, so the closure depends on how each consumer resolves it. Improving the sink list or the analyzer invalidates every cached result, which moves that cost from every query to every release. Caching is also what makes the analysis tractable at corpus scale: each package is summarized once and the summaries are composed, so the work is linear in package size rather than a whole-program analysis repeated per consumer.
- **Every claim carries the evidence that produced it: which API, in which package, at what depth.** This is what lets the analysis grow stronger over time without any published record becoming false. Adding capability to a record is additive, and nothing said earlier stops being true. Removing capability retracts a claim that consumers already hold and act on. With evidence in the record, a consumer who wants a stricter view applies their own threshold, so tightening happens on the consumer's side and the project never takes anything back.
- **State a negative result as what the analysis did not find, never as what the package cannot do.** Write "the analysis could not find a path to a network operation", not "this package cannot reach the network". Static analysis of .NET is not sound. Reflection resolves a type from a string, which leaves no reference in metadata, and `Newtonsoft.Json` emits and runs intermediate language at runtime, so no static claim about what it cannot do holds. The finer the granularity of a claim, the stronger it reads, so a negative about one method carries more risk than a negative about a whole package. The wording is what carries that risk, which is why it is fixed here rather than left to each output format.
- **The sink list leans toward under-reporting. Reachability leans toward over-reporting.** These two parts of the analysis want opposite biases, and treating them as one choice produces a tool that is wrong in both directions at once. Draw the sink list precisely, and tag an API as privileged only where that is clearly true, because a wrong entry there produces a false positive in every package that touches that API. That error is systematic and invisible, and it is what trains a consumer to ignore the output. Set the default at the type rather than at the namespace, because .NET namespaces mix operations with pure data types: `System.IO` holds `File` next to `MemoryStream`, and `System.Net.Http` holds `HttpClient` next to `HttpContentHeaders`. Measured on 2026-08-14, `Newtonsoft.Json` references seven distinct `System.IO` types and not one of them touches the file system, so a namespace-level default would report file system capability for the most-downloaded package on nuget.org. Over-approximate reachability instead. Assume every branch inside a method runs, and assume a virtual call can reach any implementation the analysis can see. That uncertainty belongs to a single package and the record can name it, which is what the evidence and wording decisions above exist for. Resolving a virtual call only to its static type would miss capability reached through interfaces and dependency injection, silently, and that covers most real .NET code.
- **NuCaps defines its own capability vocabulary and its own record format. It does not reuse the identifiers used by [Capslock](https://github.com/google/capslock).** A category's real definition is its sink list, not its one-line description. A Capslock category means "reaches one of these Go standard library functions". A NuCaps category means "reaches one of these .NET APIs". Different people draw those two sets against different libraries, so two categories can share a description and still cover different things. Reusing an identifier would assert an equivalence that does not hold, and a consumer merging the two datasets would get a wrong answer with nothing to signal it. There is also no specification to adopt: the Capslock project organization publishes a website and no shared schema, and its Java implementation consumes Google's protocol buffer file through a git submodule pointed at a personal fork. Adopting that would mean tracking another project's implementation detail, and it would put a protocol buffer dependency into a library that currently has none. Take design guidance from Capslock freely, in particular its practice of naming what the analysis could not do instead of staying silent about it. Use ordinary English words where they are the plain choice, because inventing an unusual word only to look different makes the data harder to read. The rule is narrow: a NuCaps name means what the NuCaps sink list says it means, and NuCaps never implies that its output is a drop-in substitute for another tool's.
- **Publish a table mapping NuCaps categories to the nearest Capslock ones, as documentation and not as a compatibility claim.** Real applications draw dependencies from several package ecosystems at once, and deps.dev already aggregates package data across ecosystems and consumes Capslock output. A mapping table lets someone working across ecosystems line the datasets up by hand, and, more usefully, shows where they do not line up. It costs one documentation file and commits the project to nothing, because it describes a correspondence rather than promising one.

## Testing

- **Test with TUnit.** Chosen over xUnit v3 and the in-box xUnit v2 template. Source generated, no reflection at runtime, and fast across a large corpus run.
- **`dotnet test` is the single test command.** TUnit runs on Microsoft.Testing.Platform, which the .NET 10 software development kit opts into through `global.json`. The older `TestingPlatformDotnetTestSupport` property is the legacy Visual Studio Test route and the .NET 10 software development kit rejects it.
- **Opt out of .NET and test platform telemetry, in `.envrc`.** The `TUnit` package pulls in a telemetry extension, and the software development kit reports usage of its own. A tool that reports what other packages do should not send usage data itself. `.envrc` sets `TESTINGPLATFORM_TELEMETRY_OPTOUT` and `DOTNET_CLI_TELEMETRY_OPTOUT`, and the continuous integration workflow sets the same two, because `.envrc` covers local runs only.

## Licensing and authorship

- **Apache 2.0 for code.** `NuCaps.Core` exists to be embedded, and a copyleft license would block adoption in most corporate .NET environments. Apache 2.0 also carries a patent grant and matches the surrounding ecosystem.
- **CC BY 4.0 for the capability data and the schema.** Code licenses do not fit data. Attribution keeps NuCaps named when its records are used elsewhere.
- **No AI-generated code under `src/`.** NLnet's generative AI policy states that purely AI-generated output is not eligible for copyright protection in the European Union, so such code could not be placed under Apache 2.0. Generated code in `src/` would leave part of this project unlicensed, which matters most for a library meant to be embedded. `CLAUDE.md` holds the full rule.
- **Only `src/` is the licensed work. Everything else is infrastructure around it.** The tests, the workflows, the scripts, the build configuration and the documentation ship with the project and may be used for any purpose, and no copyright is claimed over them. This follows from the rule above rather than adding to it: an assistant writes all of that material, output with no copyright cannot be placed under Apache 2.0, and pretending otherwise would leave the license claiming something untrue. Drawing the boundary at `src/` makes one line answer three separate questions, namely what a human writes, what Apache 2.0 covers, and what ships to a consumer. `CODE_OF_CONDUCT.md` is the single exception, because it is adapted from the Contributor Covenant and carries that work's CC BY-SA 4.0.

## Conventions

- **American English throughout.** Chosen for consistency with .NET and NuGet naming, which is American everywhere.
- **Plain prose commit messages. No Conventional Commits.** An imperative subject under 50 characters, and a body wrapped at 72 columns that explains why. Conventional Commits earns its place when tooling reads commit messages to compute a version number, and nothing here does that.
- **Sign commits and tags with SSH, not GPG.** Signing proves a commit came from someone holding the author's key, which matters if a GitHub token is ever stolen: an attacker can still push, but the commits show as unverified. SSH signing reuses the existing ed25519 key, so there is no second key to expire, back up, or revoke, and GitHub shows the same verified badge either way. GPG would only win if verification were needed outside GitHub through a web of trust. Signing covers the source history only. Provenance for published packages is a separate matter, handled by trusted publishing.
- **Semantic versioning, derived from git tags rather than from commit messages.** Semantic versioning is required of a published NuGet package. Deriving it from tags, with a tool such as MinVer or Nerdbank.GitVersioning, gives the same result without imposing a format on every commit. Decide the tool when publishing is set up.
- **Write `CHANGELOG.md` by hand, in the Keep a Changelog format.** Commit messages carry no Conventional Commits prefixes, which is the decision above this one, so nothing in this repository can generate release notes from history. That makes a hand-written changelog necessary rather than a nicety. It covers the software only, meaning `NuCaps.Core` and `NuCaps.Cli`. Repository changes such as workflows and documentation stay out of it, because they are readable in git history and none of them change what a user is able to do.

## Repository and continuous integration

- **Pin every GitHub Action to a commit hash, never to a version tag.** A tag is mutable. Whoever owns an action can repoint `v7` at different code, and the workflow would run that code with no change in this repository and no signal to anyone. A commit hash cannot be repointed. The cost is that hashes are unreadable, so each one carries a trailing comment naming the release it came from, and Dependabot watches the `github-actions` ecosystem to raise the updates.
- **Build on GitHub's hosted `ubuntu-latest` runner. Do not build a custom image.** The workflow installs one thing, the .NET software development kit, and that takes seconds. A custom image is a thing to build, host, scan and keep patched, and it would add supply-chain surface to a project whose subject is supply-chain risk. Revisit this if setup time ever dominates a run, or if the corpus analysis needs tools the hosted image does not carry. This is a separate question from isolating the analysis of untrusted packages, which is in Open questions below.
- **Protect `main` and the tags with repository rulesets, not with branch protection or protected tags.** GitHub deprecated both of the older mechanisms in favor of rulesets. One asymmetry matters and is easy to get wrong: `Restrict updates` is enabled on the tag ruleset, because repointing a published tag is exactly what must be blocked, and it is disabled on the branch ruleset, because there it blocks every push including your own.
- **Check the commit message convention with a local git hook, not with a workflow.** Force pushes to `main` are blocked with no bypass, so a commit message that reaches the branch can never be corrected. A workflow runs after the push, which is already too late to act on. The hook is in `.githooks/`, and `script/bootstrap` points `core.hooksPath` at it, because git does not commit `.git/hooks` and so does not share hooks by itself.
- **Do not add a prose linter such as Vale.** The Communication standard in `CLAUDE.md` governs consistency and clarity. A sentence that slips past it causes no harm and gets noticed on the next read. That does not justify a dependency, a rule set to maintain, and a build step that can fail on style.
- **Scan code with CodeQL default setup, not advanced setup.** Advanced setup writes a workflow file into this repository, which would then need its own pinned action hashes, its own Dependabot entry, and its own maintenance. Default setup is configured on GitHub and gives the same analysis for the queries this project needs. Move to advanced setup only if a custom query or a build step the default cannot perform becomes necessary.
- **Turn Copilot Autofix off, even though it is free and on by default.** Autofix suggests a code change on a code scanning alert, and GitHub enables it for every repository using CodeQL. The suggestion is generated code aimed at `src/`, so accepting one would put content into this project that carries no copyright in the European Union and therefore cannot be licensed under Apache 2.0. This is the same rule as the rest of `src/`, applied to a channel that arrives labeled as a security fix, which is exactly when a contributor is most likely to accept it without thinking. The objection is to authorship, not to quality. Detection stays on, because finding a problem is analysis and does not create anything to license.
- **Do not enable AI-powered security detections.** Three reasons hold independently. The feature analyzes pull requests only, and this project does not require pull requests yet, so it would have nothing to run on. Its purpose is to cover the languages CodeQL misses, such as PHP, Terraform and Dockerfiles, and the only one of those present here is shell, which ShellCheck already covers offline and for free. It also bundles Copilot Autofix, which this project turns off for the reason above. It further requires two paid licenses, bills usage against AI credits, and is in public preview.
- **Check shell scripts with ShellCheck in continuous integration.** The hook and the bootstrap script are executable files that no other check reads, and a broken one fails at the moment a newcomer first runs it. ShellCheck is preinstalled on the runner image, so this adds no dependency and no install step. The step finds scripts by their shebang line rather than from a fixed list, because neither script carries a `.sh` extension and a hand-maintained list goes stale. It fails when the search returns nothing, so that a broken search cannot report success.
- **Secret scanning runs with the free features only. The two extra features stay off.** Secret scanning and push protection are on, and both are free for a public repository. Validity checks and non-provider patterns are off, and they cannot be turned on here. The repository settings API accepts a request to enable either one, returns success, and leaves the setting unchanged, so nothing reports a failure to act on. The documentation page for the feature does not state what is required. The likely reason is that both belong to the paid GitHub Secret Protection tier, but that is an inference and it is not confirmed. Revisit this if the project ever holds that license, or if GitHub makes the two features free for public repositories.
- **Requiring a pull request before merging to `main` is deferred.** There is one author. A required pull request that only its own author can approve adds a step and produces no review. Adopt it when a second person contributes, because at that point it starts to carry real review instead of ceremony.
- **Requiring status checks in the branch ruleset is deferred, and belongs with pull requests.** A status check runs on a commit that already exists on GitHub. With direct pushes to `main`, the commit exists only after the push, so the rule would either block the push outright or report after the fact, and neither prevents a bad commit from landing. Enable it in the same change that requires pull requests, where a check can run on the branch before anything merges.
- **Issue templates and a `CONTRIBUTING.md` are deferred.** The capability taxonomy is not settled, so there is no stable thing to file issues about and no process for an outside contributor to follow. Writing them now would fix the shape of contribution before the shape is known. Write them before announcing the project publicly.

## Open questions

These are not decided yet. Each one is recorded here so that it gets decided deliberately rather than by accident, on the day someone first needs an answer.

- **How should the analysis be isolated when it runs over untrusted packages at scale?** `PEReader` and `MetadataReader` are not hardened against malformed input, and Microsoft documents out-of-bounds reads, crashes and hangs. So a package designed to attack the reader can take down whatever process reads it. The mitigation is to parse in an isolated process that can be killed, but the shape of that isolation is open. An operating system process with time and memory limits is the cheap answer. A purpose-built container with no network access, a read-only file system, and hard resource limits is the strong answer, and it costs an image to build, host, scan and keep patched, which is real surface for a project whose subject is supply-chain risk. This becomes pressing at corpus scale, where thousands of packages are analyzed unattended, and it does not need answering before then. It is a separate question from the continuous integration runner image, which needs no customization.
- **How should a per-package summary represent a call the analysis cannot resolve?** A capability claim is composed from per-package summaries, so a summary has to describe calls whose destination is not known when the package is analyzed alone. Two cases matter. A package calls through an interface or a delegate that the consumer implements, so the destination is chosen outside the package. A package uses reflection, so the destination is a string and there is no reference in metadata at all. The summary could record an unresolved edge that composition tries to close later, or it could record the call site as a named gap that surfaces in the record, or it could do both. This decides how much of the analysis is honest about its own blind spots, so it needs answering before the record format is fixed.
- **How much does a per-package summary actually cost to compute?** The decision to analyze every method rests on the claim that summarizing one package is linear in its size and cheap enough to run over the corpus. That claim is reasoning, not measurement, because no metadata reader exists yet. Measure it on the first working version against `AWSSDK.S3` and `Azure.Storage.Blobs`, which are already the largest packages in the test corpus. If it is far more expensive than expected, the fallback is to publish at a coarser granularity while keeping the record format unchanged, because the format carries evidence and can hold either.
- **Where do changes to the capability records and the schema get written down?** `CHANGELOG.md` covers the software and says so in its own opening. The records and the schema are versioned separately because they have their own lifecycle, but nothing yet says where their changes are recorded or in what format. Answer this before the first schema is published. Somebody who builds against a record format needs a way to learn that it changed, and deciding after publication means the first change is the one with nowhere to go.
